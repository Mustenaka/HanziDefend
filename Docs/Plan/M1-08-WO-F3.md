# WO-F3 · 部署格 = 兵营：按冷却持续出兵

> 优先级高于 WO-F1 剩余的数值收敛。**F3 不落地，F1 的数值收敛做多少废多少**——
> 一次性投入与持续出兵是两个量级完全不同的口径。

---

## §0 这是一条丢失的需求，不是新增设计

| 出处 | 原话 |
|---|---|
| `Docs/Note/拆解文档.md` §36 | 「自动根据**部署和冷却情况**，出兵」 |
| 同上 §38 | 「战斗的节奏是**偏弹幕式**的，我方出兵较多，敌方出兵也较多，各类兵种（一些特殊兵种除外），**是极易死亡的**」 |
| `M1-00` §3.1（压缩后） | 「`Instant` 开局即出，`Delayed` 冷却到期出」 ← **一次性，丢了「持续」** |
| WO-F1 §B（照抄 M1-00） | 实现成一次性入场队列 |

用户试玩原话：

> 卒、弓这类 1×1 的基本单位，很容易出现，进入部署之后也可以非常快地再部署，在战斗中刷新生成出来。
> **这个刷新不能是前面的死了才刷新，而是 CD 到了就可以刷新，形成一种兵海的感觉。**

**本单要还原的就是这个。** `M1-00` §3.1 那句要按拆解文档改写，不是"新增契约"而是"订正契约"。

## §A 要求

1. **每个部署格是一个独立的出兵源**（键用已有的 `DeploymentPlacement.DeploymentId`，不要新造 id）。
2. **首次出场时间 = 该单位的 `cooldown`**（WO-F1 §B 已实现的行为保留：大兵不在开局出现）。
3. **之后按 `cooldown` 周期性持续出兵，与前一个是否存活无关。**
4. **每格有同时存活上限**，否则站在后排不死的弓/弩车会无限堆叠。
   上限按占格数分档（首版参考：1 格 → 4，2 格 → 2，3~4 格 → 1），**进数据不要写死在代码里**。
   达到上限时不产出；**冷却计时怎么处理由你定**（暂停 / 继续空转），但要在 `DECISIONS.md` 写清选了哪个、为什么。
5. 排队/未出场的单位仍然**不存在于战场**（不占位、不被索敌、不吃 AOE、不进结算）——WO-F1 §B 这条不变。
6. 局内携带的持久 BUFF 要能补给**每一批**新出场的单位（WO-F1 已有 `RegisterPersistentAllyEffect` 的机制，沿用）。

### 现有冷却值当作出兵间隔的量级（先量后改的起点）

| 单位 | 格 | CD | HP | 每分钟产出 | 每格 HP 吞吐/秒 |
|---|--:|--:|--:|--:|--:|
| 卒 | 1 | 1.2 | 70 | 50.0 | 58.3 |
| 弓 | 1 | 2.2 | 90 | 27.3 | 40.9 |
| 肉盾 | 2 | 3.5 | 900 | 17.1 | 257.1 |
| 铁甲/链甲 | 4 | 7.0 | 1600 | 8.6 | 228.6 |
| 弩车 | 3 | 8.0 | 700 | 7.5 | 87.5 |

对照：现在 S5 棋盘 11 个单位**一次性**投入约 6,000~8,000 HP。
改成兵营后，**光 4 个卒格在 110 秒里就能投出 25,667 HP**。

⇒ **这套 CD 值是按「一次性延迟」定的，当作出兵间隔多半整体偏快。** 重新定档是本单的一部分，
但要先跑出数再改，并且把「首出延迟」与「出兵间隔」是否共用一个数这件事明确下来
（**倾向共用一个 `cooldown`**，靠每格存活上限来区分兵海与单件——大单位上限 1 时，
CD 驱动与死亡驱动自然收敛成同一件事。若实测证明必须拆成两个字段，给数据依据再拆）。

## §B 连带影响（必须一并处理，否则本单落地即崩）

1. **性能是本单第一风险。** 双方兵海，场上实体数会数倍增长。
   现有门禁是 200 单位 ≥60fps（Editor ≥45）。**要有一条我方场上实体上限**，并上报峰值。
   触到上限时的行为要定义（停止产出 / 排队），不要变成不可预测的掉帧。
2. **敌军预算全部作废，需重推。** 好消息是 WO-F1 §A.2 的框架仍然成立
   （`预算 = 实测DPS × 幕时长 × 压力系数 × 每关难度系数`），因为它本来就是 DPS 驱动的；
   变的只是"实测DPS"从一次性衰减量变成可持续量。**本单只负责把机制做对并报出新的 DPS 读数，不负责调平胜率。**
3. **经济会再次被冲垮**：敌人死得更多 → 掉币更多。本单报出新的每场掉币总额即可，调价留给收敛轮。
4. **`allyAdvanceLimitY` 的意义变了**：有源源不断的兵之后，前线自然形成，推进上限可能不再需要。
   报出「拿掉它 / 保留它」两种情况下的前线位置对比，让下一轮决定。

## §C 验收标准

1. 用例钉住三条机制：①首出时间 = `cooldown` ②**前一个还活着时，CD 到期仍会出下一个**
   ③达到每格上限时不再产出、有单位死亡后恢复产出。第 ② 条是本单的核心，塞回旧实现必须红。
2. 每格存活上限走数据 + 加载期校验（上限为正、与占格数的分档关系可读）。
3. 报出四个数：**新的每关实测有效 DPS**、**我方场上实体峰值**、**每场掉币总额**、
   **有/无 `allyAdvanceLimitY` 两种情况下的前线位置对比**。
4. 现有性能门禁全绿（若因兵海变红，先给实体上限，再报为什么这个上限是够用的）。
5. `M1-00` §3.1 那句按拆解文档订正；`DECISIONS.md` 记冷却计时策略、上限分档依据、CD 重新定档的推导。
6. 收工自检五项（M1-03 §4）。

## §D 边界

- **不负责调平胜率。** 四条目标区间与 `[Ignore]` 留在 WO-F1 的收敛轮，本单不碰。
- 不改 `damage.typeMultipliers`；不改 M1-04 §3 的单位属性表（`cooldown` 重新定档除外，且要给依据）。
- 不改 WO-F1 已通过的四项（城堡索敌修法、城堡数值、胜负谓词、压力系数语义）。
- 合成零收益（`growth` 全 0）仍归 WO-F2，本单不碰。
