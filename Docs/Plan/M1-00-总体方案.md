## 2. 技术选型与架构

### 2.1 引擎与渲染
- Unity **6000.3.11f1** + URP，新建 **2D Renderer**（现有 PC/Mobile Renderer 是 3D 配置，保留但不用于游戏场景）
- 全部 Sprite + Unlit，**无实时光、无阴影、无后处理、关 HDR**
- 分辨率基准 **1080×1920 竖屏**，PPU = 100（→ 世界尺寸 10.8 × 19.2）
- CanvasScaler：`ScaleWithScreenSize`，参考 1080×1920，`match = 0.5`

> 终点是微信小游戏。以上每条都是「现在做免费、以后改很贵」的约束，全部前置。

### 2.2 分层

```
Assets/Scripts/
  Data/      [HanziDefend.Data]           纯 C#。POCO 契约、JSON 读写、数值公式、确定性 Rng
  Gameplay/  [HanziDefend.Gameplay]       Unity C#。玩法系统，引擎能力随便用
  View/      [HanziDefend.View]           表现层、UI、输入、音频
  Editor/    [HanziDefend.Editor]         工具链：JSON 编辑器、美术导入、生成器、截图
  Tests/
    EditMode/  [HanziDefend.Tests.EditMode]
    PlayMode/  [HanziDefend.Tests.PlayMode]
```

`Data` 层保持纯 C#（它本来就只有数据结构和公式，不需要引擎）。
`Gameplay` 层**可以自由使用 Physics2D、Transform、协程、对象池等一切引擎能力**——这是玩法逻辑该待的地方，也是未来若上 Lua 时会被替换的那一层。

### 2.3 两条硬要求（替代原先的"禁用 UnityEngine"）

**① Tick 可手动驱动**
`BattleSystem.Tick(float dt)` 必须是测试代码能连续调用 N 次的公开方法，玩法逻辑不得埋在 `Update()` 里依赖真实帧率。

物理同样可手动步进：
```csharp
Physics2D.simulationMode = SimulationMode2D.Script;   // 战斗场景初始化时
Physics2D.Simulate(dt);                                // 每个逻辑 tick 手动推进
```
这样即使将来引入物理，也不影响无头批跑 100 局调数值——两者不冲突。

> **2026-08-13 更新（WO-B5）**：索敌已改为**纯 C# 确定性空间桶**，战斗实体不再挂 `Rigidbody2D` / `Collider2D`。
> `simulationMode = Script` 与每 Tick 的 `Simulate(dt)` 予以保留，作为「将来若引入物理即已就位」的挂钩，
> 当前不参与索敌。

**② 随机走 `Data.Rng`（带 seed）**
禁止 `UnityEngine.Random`。保证 bug 可复现、批跑可对拍、同 seed 结果一致。

除这两条外，`Gameplay` 层怎么实现是施工方的自由。

### 2.5 数据：JSON 为唯一真源 + 可视化编辑器

```
Assets/GameData/
  units.json          兵种/敌方/BOSS
  commanders.json     指挥官
  waves.json          波次编排
  levels.json         关卡
  effects.json        BUFF / 技能（效果指令，见 §2.7）
  economy.json        刷新费用曲线、掉落、卡池权重
  art_manifest.json   [自动生成] id → 贴图路径
```

- 数值改动是纯文本 diff，好改好审，天生热更友好
- 结构按 `JsonUtility` 友好方式设计（数组代替字典、枚举用字符串 + 映射表）
- **配套 JSON 数据编辑器（WO-02）**：`JSON ⇄ 影子 ScriptableObject ⇄ 原生 Inspector`，带表格视图批量改数值、schema 校验、保存前 diff 预览。影子 SO 不入库，JSON 始终是真源。
- **自由条款**：若 `JsonUtility` 实在别扭，可自行引入 `com.unity.nuget.newtonsoft-json` 或手写解析器，记 `DECISIONS.md` 即可。

### 2.6 美术绑定与场景装配：两处结构性规避

**美术走约定路径，不手拖引用**
```
Assets/Art/Units/{unitId}/idle.png | attack.png
Assets/Art/UI/{name}.png
Assets/Art/Battlefield/{name}.png
```
Editor 工具扫目录生成 `art_manifest.json`，运行期用 id 取图，**没有任何一处需要在 Inspector 拖引用**。

**场景由代码装配，不手搓 YAML**
- `Assets/Scenes/Battle.unity` 只有 3 个对象：`Main Camera`、`Canvas`、`Bootstrap`
- `Bootstrap` 在 `Awake` 装配整个场景
- 需要 Prefab 的由 Editor 菜单 `HanziDefend/Rebuild Prefabs` 生成
- 所有产出都是可 review 的 C# diff，不会出现场景冲突/丢引用这类反复返工

### 2.7 热更立场：M1 用「数据热更」覆盖需求

M1 不引入 xLua / HybridCLR。取而代之：**技能与 BUFF 做成「效果指令」数据**，由 `Gameplay` 层的 C# 解释器执行。

```json
{ "id": "buff_atk_up", "name": "锐意",
  "ops": [ { "op": "AddStat", "stat": "atk", "mode": "mul", "value": 0.10,
             "target": "AllyAll", "duration": -1 } ] }
```

M1 支持的 op（够用即可，别过度设计）：
`AddStat` / `Heal` / `Damage` / `GrantShield` / `SpawnUnit` / `ModifyCoins`
target：`SelfUnit` / `AllyAll` / `AllyAdjacent` / `EnemyNearest` / `EnemyInRadius` / `EnemyBase`

这样热更粒度正好落在最需要热更的地方——数值与技能平衡。M3 真要上 Lua，替换的是这个解释器，不是重写玩法，且届时有完整 C# 参照实现与单测可对拍。

**xLua / HybridCLR 决策时机**：M2 结束时做一次热更需求评估（真需要逻辑热更吗？小游戏审核实际多快？HybridCLR 在 WebGL/wasm 的实测结果如何？）。HybridCLR 的 WebGL 支持**未在本环境验证过**，届时需单独 spike，不预先押注。

### 2.8 战斗循环
- **固定步长 30Hz** 累加器驱动 `BattleSystem.Tick(1f/30f)`，表现层插值
- 单位**不各自挂 Update**，由系统统一遍历（DrawCall 与 GC 友好）
- 索敌用**纯 C# 确定性空间桶**（WO-B5 起；此前为 `Physics2D.OverlapCircle`），重定向节流默认 0.2s 一次
  - ⚠️ 重定向**尚未做相位错开**，同波出生的单位会同步尖峰。见 `REVIEW/WO-B5.md` 建议 1

## 3. 数据契约（字段名可微调，语义不许改）

### 3.1 UnitDef
```
id            string     "gong" / "dun" / "mao" ...
name          string     "弓"（显示用汉字）
displayName   string     "弓箭手"
faction       enum       Ally | Enemy | Boss
tier          enum       Green=1 | Blue=2 | Purple=3 | Gold=4
gridW,gridH   int        占格外接宽高（1x1 / 2x1 / 1x2 / 2x2 / 3x1）
footprint     enum       Rectangle / MissingUpperRight / MissingLowerLeft
layer         enum       Ground | Air        （M1 全 Ground）
spawnMode     enum       Instant | Delayed
targeting     enum       Nearest | Backline | RushBase | Suicide
effects       string[]   自带效果 id（指向 effects.json）

// 克制系统（详见 M1-04）
unitType      enum       步兵 | 骑兵 | 水兵 | 空军 | 建筑 | 特殊
armorType     enum       无甲 | 轻甲 | 重甲 | 建筑
atkType       enum       斩击 | 打击 | 弓箭 | 器械 | None（光环单位）
bonusVs       [{target,value}]   对位加算伤害，target 可为兵种类型或护甲类型

// 每项都是 {base, growth}，等级 L(1..4) 的值 = base * (1 + growth * (L-1))
hp, atk, range, atkSpeed, cooldown, armor, pierce, moveSpeed
```

### 3.2 其余
- `CommanderDef`：`id, name, passiveEffectId, activeEffectId, activeCooldown`
- `BaseDef`：`hp, armor`
- `BossDef`：`BaseDef` + `atk, range, atkSpeed, pierce, effects[]`（BOSS 不等于基地，可开火）
- `WaveDef`：`index, delaySec, spawns[{unitId, count, spreadX, intervalSec}]`
- `LevelDef`：`id, stageIndex, waveSetId, baseHp, startCoins, gridWidth, gridHeight, initialUnlock{col,row,width,height}`
- `EffectDef`：`id, name, desc, rarity, ops[]`（见 §2.7）
- `RunState`（跨小关继承）：`coins, deployedGrid, ownedEffects[], refreshCount, stageIndex, seed, gridWidth, gridHeight, unlockedCells[49], unlockPurchaseCount`

### 3.3 公式（定死，写单测锁住）
```
armorMitig = max(0, armor - pierce) / (max(0, armor - pierce) + 100)
typeMult   = 克制矩阵[被击方 armorType][攻击方 atkType]      // 见 M1-04 §2.1
bonus      = Σ 攻击方 bonusVs 中命中被击方 unitType/armorType 的加值
damage     = max(1, round( (atk × typeMult + bonus) × (1 - armorMitig) ))

// 旧公式（已被上式取代，保留供追溯）
effectiveArmor = max(0, armor - pierce)
mitigation     = effectiveArmor / (effectiveArmor + 100)
damage         = max(1, round(atk * (1 - mitigation)))

属性(L)     = base * (1 + growth * (L - 1))      L ∈ [1,4]
刷新费用(n) = 15 + 5 * n                          n = 本小关已刷新次数
掉落金币    = 普通 1 / 精英 3 / BOSS 20
```

## 4. 三阶段规则

### 4.1 战前部署
1. 按 `RunState` 恢复网格与金币；第 1 小关用 `LevelDef` 初始值
2. 发手牌：默认 3 张，**10% 概率发 4 张**
3. 卡池权重（`economy.json` 可调）：兵器卡 70% / **解锁卡** 15% / 增益卡 12% / 全局效果卡 3%
   - 全部 49 格解锁后解锁卡权重归 0 并重分配
   - 兵种卡是否入池按「当前已解锁区放不放得下该形状」判定，不再有列数门槛
4. 拖卡到网格 → 校验占格 → 落位；拖到同 id 同等级单位上 → 合成升级
5. 金币消耗：刷新手牌（费用递增）、购买解锁卡（`40 + 20n`，随机一张，可自选贴哪里）
   - 解锁卡另有两条免费途径：看广告、卡池抽到；打出解锁卡本身不收费
6. 每通过一个小关，自动解锁一格「离我方基地最近且贴合已解锁区」的格子（确定性，不消耗 RNG）
7. 「战斗」按钮 → 战斗阶段

### 4.2 战斗中
1. 部署网格 (col,row) 映射到我方基地前方出生坐标；`Instant` 开局即出，`Delayed` 冷却到期出
2. 索敌四策略：`Nearest` / `Backline`（优先最远排）/ `RushBase`（直取敌方基地）/ `Suicide`（接触自爆 AOE）
3. 20 波：前 18 波小兵递增，第 19 波精英潮，第 20 波 BOSS 登场
4. 受击显血条（我方蓝 / 敌方红），2 秒无受击隐藏
5. 击杀掉金币累加到 `RunState`
6. 指挥官主动技能：左上角按钮，冷却制
7. **胜负判定单一出口** `TrySettle()`：`Result ∈ {None, Win, Lose}`，一旦非 None 立即冻结 tick。必须有回归测试覆盖「同帧我方基地与 BOSS 同时归零」——需求文档点名要求
8. 调试开关：自动出兵 / 手动出兵切换

### 4.3 战斗结算
1. 随机发 3 张（BUFF 85% / 主动技能 15%）
2. 每张**免费重随 1 次**；`IAdService.ShowRewarded()` 成功后再给 1 次（M1 用 `MockAdService` 直接返回成功）
3. 选中 1 张进 `RunState.ownedEffects` → 下一小关部署
4. 第 5 小关通关 → 大关结束页 → 重置 `RunState`

## 6. 风险与预案

| 风险 | 触发信号 | 预案 |
|---|---|---|
| gpt-image2 写错汉字字形 | contact sheet 里字形错/缺笔 | 改用**参考图引导**（喂标准正楷图走图生图）；仍不行则该字换一个同义汉字 |

| 200 单位同屏掉帧 | Profiler 帧时间超标 | 对象池 + 索敌节流 + SpriteAtlas（WO-E3 已规划） |
| 后期发现真需要逻辑热更 | M2 末评估结论 | `Gameplay` 层边界已划清，替换解释器即可，不需重写玩法 |
